01

最小 Agent Loop｜讓模型與工具一起工作

模型如何根據工具結果，決定下一步並停下來？

先從最小的情境開始：一個 Agent Runtime（負責執行 Agent 的那一層）、一次執行。使用者請它找出登入失敗的原因。這一章只回答一件事：模型怎麼取得需要的資訊、看到行動的結果，再決定要繼續還是結束？等看清這一層的責任，後面才往外加上管理整個任務的 Task Orchestrator。

模型說「可能是登入驗證」，但它還沒看過程式

只把問題交給模型，它可以提出猜測，卻不知道專案裡真正寫了什麼。你給它一個 readFile 工具，讓它能看登入程式。新問題隨之而來：誰真的去讀檔案？讀完的結果怎麼送回模型？

1. 先完成一次「提出行動 → 執行 → 回傳結果」

模型回傳工具名稱與參數，是提出一個行動請求。Agent Runtime 的程式負責檢查請求、呼叫工具，再把結果交回去。模型本身沒有因為說出 readFile，就真的讀到檔案。

2. 把結果帶回去，就形成循環

每一輪都做三件事：把目前資訊交給模型、接收它的決策、執行被允許的工具並保存結果。接著回到第一件事。這就是本章的最小 Agent Loop。

目標 + 目前資訊 → 模型決策
       ↑             ├─ 工具請求 → 檢查 → 執行工具 → 結果
       └─────────────┴────────────────────────────┘
                     └─ 完成提案 → 驗收 → 成功／未通過

模型選擇接下來要做什麼；執行程式決定什麼可以做、怎麼執行，以及如何處理結果。這個分工讓模型能動態選路，也讓工具權限留在程式中。

3. 「完成」是提案，停止由執行程式把關

模型可能持續要求同一個檔案，也可能在證據不足時宣告完成。因此我們先加兩個簡單邊界：最多執行三次工具，以及完成提案必須經過驗收。驗收應依目標設計；找原因可以要求檔案與證據，修程式則還需要修補產物與測試結果。

TypeScript · 教學介面／假模型示例
type Decision =
  | { kind: "tool"; name: string; args: unknown }
  | { kind: "finish"; answer: string };
type Observation = { name: string; result: string };
type Context = { goal: string; observations: Observation[] };

// 自訂教學介面，不是 LangGraph SDK API。
async function runAgent(context: Context, deps: {
  decide: (context: Context) => Promise<Decision>;
  validateAndAuthorize: (decision: Decision) => void;
  execute: (decision: Decision) => Promise<Observation>;
  verify: (answer: string, context: Context) => Promise<boolean>;
}, maxActions = 3) {
  let actions = 0;
  while (true) {
    const decision = await deps.decide(context);
    if (decision.kind === "finish") {
      const passed = await deps.verify(decision.answer, context);
      return { status: passed ? "completed" : "verification_failed",
        answer: decision.answer, actions };
    }
    if (actions >= maxActions) return { status: "budget_exhausted", actions };
    deps.validateAndAuthorize(decision);
    const observation = await deps.execute(decision);
    context.observations.push(observation);
    actions += 1;
  }
}
// 範例只限制工具次數，最多呼叫模型 maxActions + 1 次。
// 例外會傳給呼叫者；尚未處理重試、逾時、取消與跨程序恢復。

有一個順序細節：用完三次工具後，模型還有一次機會讀取第三次的結果並提出完成；如果它又要求工具，才回傳 budget_exhausted。這個上限只防止工具回合無限增加；單次模型或工具如果卡住，之後還要另外加時間限制。

02

Agent State｜讓每一輪都有明確的起點

Agent Runtime 要記住什麼，才知道現在可以做哪一步？

上一章，Agent Runtime 讀取登入程式，把結果交回模型，再根據證據提出結論。這個循環已經能走完，但資訊分散在 context、actions 和函式的執行位置裡，沒有一個地方能一眼看出「現在做到哪了」。

現在把調查拉長一點：讀完登入程式後，模型想查看測試檔，卻發現需要使用者補充檔案位置。Agent Runtime 暫時不能繼續。它該記住哪些資訊，才能在收到回覆後接著工作？又怎麼區分「正在等工具」和「正在等使用者」？

只保留聊天紀錄，足以知道下一步嗎？

聊天紀錄可以保存問題與工具結果，但執行程式還需要一些明確欄位：目前目標、已取得的證據、尚未完成的工具請求、已使用的工具次數，以及目前處於哪個階段。若每次都從聊天文字猜測這些資訊，程式很難一致地判斷下一步。

我們先把本次執行需要的資料收進一個物件。模型需要什麼上下文，可以從這個物件挑選；程式也可以直接根據它判斷是否允許執行工具。

核心概念 · Agent State

State 是聊天紀錄，還是執行狀態？

Agent State 是本次執行的資料快照；phase 只是其中一個欄位。看到 phase = acting，我們知道正在處理工具，但還要讀 pendingTool，才知道是哪個工具與哪些參數。

模型 Context 是這一次送給模型的資訊，通常由 state 中的目標、證據與相關訊息組成。它不必包含所有內部欄位。未來接 LangGraph 時，共享 state 會成為節點之間交換資料的基礎；本章先用普通 TypeScript 理解它。

這個 schema 是教材設計。LangGraph 的 State 概念支持共享資料與更新規則，但沒有要求 Agent 必須採用這七個 phase。官方 State 說明 ↗

有了 phase，就可以任意把它改成 completed 嗎？

假設 Agent Runtime 還在等待工具，卻收到一個「驗收通過」事件。若程式直接覆寫 phase，就會在沒有結果時宣告成功。我們需要規則：哪些事件可以在目前階段發生？發生後該到哪裡？

把上一章的循環展開：模型提出工具請求時進入 acting；工具回傳後，帶著新證據回到 thinking；模型提出完成時，先進入 verifying，驗收通過才到 completed。需要補充資料時則進入 waiting，收到回覆後再回到 thinking。

thinking ─工具請求→ acting ─工具結果→ thinking
    ├─需要補充→ waiting ─收到回覆→ thinking
    ├─完成提案→ verifying ─通過→ completed
    │                      └─未通過→ failed
    └─工具額度用完→ budget_exhausted
acting ─工具失敗→ failed（本章先停止，下一章研究重試）
核心概念 · State Machine

怎麼把「可以做哪一步」寫成共同規則？

狀態機（State Machine） 用目前狀態與輸入事件決定下一個狀態。它讓「現在是否能接受工具結果」成為程式規則，而不是散落在不同地方的猜測。

這裡的狀態機很簡單，沒有階層或平行狀態。waiting 只表示這次執行在等資料，不是失敗，也不會自動保存或恢復。

工具回來時，除了 phase 還要更新什麼？

工具成功不只是 acting → thinking。我們還得加入證據、清除 pendingTool，並把 actions 加一。這些欄位應一起更新，避免「已回到 thinking，卻還留著待執行工具」這種矛盾。

我們把規則集中到一個純函式：輸入舊 state 與事件，回傳新 state。它不呼叫模型或工具；外層執行程式完成操作後，再把事件交進來。

TypeScript · 純函式教學範例
type AgentEvent =
  | { kind: "tool_requested"; tool: ToolRequest }
  | { kind: "tool_succeeded"; result: string }
  | { kind: "tool_failed"; error: string }
  | { kind: "input_needed" }
  | { kind: "input_received"; text: string }
  | { kind: "finish_proposed"; answer: string }
  | { kind: "verification_passed" }
  | { kind: "verification_failed"; error: string };

function reduceAgent(state: AgentState, event: AgentEvent): AgentState {
  if (state.phase === "thinking") {
    if (event.kind === "tool_requested") {
      if (state.actions >= state.maxActions)
        return { ...state, phase: "budget_exhausted" };
      return { ...state, phase: "acting", pendingTool: event.tool };
    }
    if (event.kind === "input_needed")
      return { ...state, phase: "waiting" };
    if (event.kind === "finish_proposed")
      return { ...state, phase: "verifying", answer: event.answer };
  }
  if (state.phase === "acting") {
    if (event.kind === "tool_succeeded")
      return { ...state, phase: "thinking", pendingTool: null,
        actions: state.actions + 1,
        observations: [...state.observations, event.result] };
    if (event.kind === "tool_failed")
      return { ...state, phase: "failed", error: event.error };
  }
  if (state.phase === "waiting" && event.kind === "input_received")
    return { ...state, phase: "thinking",
      observations: [...state.observations, event.text] };
  if (state.phase === "verifying") {
    if (event.kind === "verification_passed")
      return { ...state, phase: "completed" };
    if (event.kind === "verification_failed")
      return { ...state, phase: "failed", error: event.error };
  }
  throw new Error(`不允許：${state.phase} + ${event.kind}`);
}
// 工具授權、模型輸出驗證與真正的驗收由外層完成。
// 本章不處理重複事件、併發提交或持久化。

假如 state 是 acting，送進 tool_succeeded，就會得到一份新的 thinking state。若此時送進 verification_passed，函式會拒絕。這讓資料更新與控制流程遵守同一套規則。

這個函式為什麼叫 Reducer？它與 LangGraph Reducer 相同嗎？

本章的 reducer 把「舊 state + 事件」折疊成新 state，並檢查整個 Agent 的階段轉移。LangGraph 的 reducer 則是各個 state「欄位」的合併規則，例如覆寫值或合併訊息；控制路徑由節點與邊決定。兩者都有「合併更新」的概念，但本章的函式不能直接當成 LangGraph 的欄位 reducer 使用。

同樣是失敗，為什麼有時能重試，有時不能？

讀取測試與建立留言，對外部世界的影響不同。讀取通常不新增業務資料；建立留言會改變系統。這種超出函式回傳值、發生在外部的變化，叫做副作用（Side Effect）。判斷重試之前，要先知道工具會留下什麼效果。

再看失敗原因。測試路徑寫錯，再讀三次也找不到檔案；權限不足，需要處理權限；短暫連線故障則可能在稍後恢復。Agent Runtime 應依工具契約與錯誤分類決定下一步，模型可以提出建議，執行程式仍要限制哪些操作允許重試。

CONCEPT / RETRY & TIMEOUT

重試是另一次執行；逾時是停止等待

重試（Retry）是再呼叫一次；如果是寫入，可能再產生一次副作用。逾時（Timeout）只是「不等了」，不能證明遠端沒做成。工具能不能取消、取消有沒有生效，要另外確認。

既然可以重試，為什麼不立刻一直試？

假設測試服務正忙，所有 Agent Runtime 都立刻重送，新的請求會讓它更難恢復。因此我們要限制嘗試次數，並在兩次之間等一會兒。等待逐步拉長叫 Backoff；加入隨機等待叫 Jitter，讓同時失敗的呼叫者比較不會一起回來。

下面先只處理「已確認可以安全重試的讀取」。錯誤由工具 adapter 分類，最多嘗試三次；每次等待的上限逐步加大，實際等多久則在零到上限之間隨機選，這是 full jitter 的簡化寫法。

TypeScript · 可執行概念範例
type ToolError = { kind: "temporary" | "invalid" | "forbidden" };
const sleep = (ms: number) => new Promise(r => setTimeout(r, ms));

// 只用於已確認可安全重試的讀取操作。
async function retryRead<T>(
  read: () => Promise<T>,
  classify: (error: unknown) => ToolError
): Promise<T> {
  for (let attempt = 1; attempt <= 3; attempt++) {
    try { return await read(); }
    catch (error) {
      if (classify(error).kind !== "temporary" || attempt === 3) {
        throw error;
      }
      const ceiling = Math.min(1000, 200 * 2 ** (attempt - 1));
      await sleep(Math.random() * ceiling); // full jitter
    }
  }
  throw new Error("unreachable");
}
// 三次包含首次呼叫；這是教材政策，不是 SDK 預設。
// 本例未設總期限與取消。正式呼叫需在工具邊界實作。

讀取重試成功後，才把一份成功結果交回第二章的狀態轉移；每次連線嘗試另外記錄。要分清兩種計數：一次「邏輯工具行動」，和它底下的多次「執行嘗試」。就算全部失敗，呼叫仍會花時間與費用，要計入總預算。

工具已有重試，外層還能再重試嗎？

若工具 SDK 嘗試三次，Agent Runtime 又呼叫它三次，就可能送出九次請求。先確認哪一層負責重試，讓其他層接收明確結果；之後接上 Temporal 時也要檢查 Activity 與工具 SDK 的政策。

用 Promise.race 回傳逾時，只能讓呼叫者提早拿到錯誤。要停止底層工作，需要工具支援取消訊號；遠端已提交的效果仍可能存在。

留言已經建立，只是回應遺失，該怎麼辦？

回到建立留言。Agent Runtime 發出請求，issue 服務保存留言，但回程連線中斷。Agent State 裡沒有 receipt，外部卻已有一則留言。現在應記錄「結果未知」（Unknown Outcome），而不是直接斷言失敗且沒有副作用。

Agent Runtime                Issue 服務
   │ ── 建立留言 ───────→ │
   │                       ├─ 留言已保存
   │ ←── 成功回應 ── ✕ ─── │
   └─ 逾時：結果未知       └─ 外部效果已發生

如果服務接受一個穩定的操作識別，重送時就能表示：「我要的是剛才那次留言，請不要再建立一份。」這個識別常叫 Idempotency Key。本章用 opId 表示一個邏輯操作；同一操作的每次重試，都沿用它。

CONCEPT / IDEMPOTENCY

重送同一操作，不增加額外效果

冪等性（Idempotency）的意思是：同一個操作重送多次，外部效果仍只發生一次。Key 讓服務認出「這是同一個意圖」，但服務端還要真的實作去重並回傳原結果才算數。每次嘗試都換新 key，就變成不同的操作；只在 prompt 裡叫模型「不要重複」，也做不到這個保證。

只要把 opId 放進請求，就已經安全了嗎？

還要看接收的服務怎麼處理。下面用假的 issue 服務示範：第一次請求保存留言與 receipt；重送時回傳既有的 receipt；同一個 key 但內容不同，就拒絕。重點是：去重必須在產生效果的那個服務裡完成。

TypeScript · 可執行概念範例
type Request = { opId: string; issueId: string; body: string };
type Receipt = { commentId: string };
const ledger = new Map<string, { args: string; receipt: Receipt }>();
const comments: string[] = [];

// 假服務：同步完成檢查、寫入與 receipt 紀錄。
function createComment(request: Request): Receipt {
  const args = JSON.stringify([request.issueId, request.body]);
  const existing = ledger.get(request.opId);
  if (existing) {
    if (existing.args !== args) throw new Error("key_conflict");
    return existing.receipt;
  }
  const receipt = { commentId: `comment-${comments.length + 1}` };
  comments.push(request.body);
  ledger.set(request.opId, { args, receipt });
  return receipt;
}
const operation: Request = {
  opId: "investigation-42:report-1", // 在首次呼叫前建立並保存
  issueId: "login-42", body: "登入驗證未排除空白 token。"
};
createComment(operation); // 假設成功後，回應在網路上遺失
const receipt = createComment(operation); // 相同 opId 與參數
console.log(comments.length, receipt.commentId); // 1, comment-1
// 這個 Map 只示範單程序；重啟後會遺失，也不是遠端 API 包裝器。
進階閱讀：同時重送與原子提交

如果兩個相同請求同時到達，或服務在寫入後崩潰，檢查與保存之間就可能出現縫隙。正式服務要讓效果與去重紀錄原子提交，並定義 key 的範圍與保留期限。上面的同步 Map 用來觀察契約，不能提供跨程序保證。

如果 Agent Runtime 只是先把 opId 寫進自己的資料庫，再去呼叫一個不支援冪等的外部留言 API，兩個系統之間仍然有縫隙。這時要查詢遠端的 receipt 或對帳；真的無法判斷，就保留 unknown，交給明確的處理流程，不能靠本機紀錄假設遠端只發生了一次。

CONCEPT / STATE · NODE · EDGE

資料、工作與路由，分別放在哪裡？

State 保存共享資料；Node 是讀取 state、執行工作並回傳更新的函式；Edge 指定後續節點。LangGraph 用這些構件組織流程。節點可以呼叫模型，也可以只是普通程式。

第二章的 phase 是業務階段，圖上的節點是執行單位，兩者不必一一對應。另外，圖引擎只負責安排下一個節點，不會自動懂你的驗收或授權規則。

模型說「完成」，箭頭就該直接走到 END 嗎？

我們仍要保留第一章的驗收。model 提出的 finish 只是要走向 verify；真正的 completed 由驗收結果決定。另一方面，工具額度用完也會走到 END，但 outcome 應是 budget_exhausted。圖停止與任務成功是兩件需要分別表達的事。

這裡需要一條會看資料選路的邊：模型要求工具且還有額度，走 tool；要求工具但沒額度，走 stop；提出結論，走 verify。這種邊叫條件邊（Conditional Edge）。它只決定「下一步去哪」；檢查請求、執行副作用仍然是節點裡的責任。

怎麼把剛才的流程變成可執行程式？

先用假模型和假的讀檔，讓每次結果固定，專心看路由。下面用官方文件目前的 StateSchema API 定義資料、加入節點與邊，再 compile 成可執行的圖；invoke 傳入這次的初始資料，最後回傳結果。

TypeScript · LangGraph SDK／假模型與工具
import { StateSchema, StateGraph, START, END } from "@langchain/langgraph";
import { z } from "zod/v4";

const State = new StateSchema({
  evidence: z.array(z.string()),
  actions: z.number(), maxActions: z.number(),
  decision: z.enum(["tool", "finish"]),
  answer: z.string(),
  outcome: z.enum(["running", "completed", "rejected", "budget_exhausted"])
});

const graph = new StateGraph(State)
  .addNode("model", s => s.evidence.length === 0
    ? { decision: "tool" as const }
    : { decision: "finish" as const,
        answer: "登入驗證未排除空白 token。" })
  .addNode("tool", s => ({
    evidence: [...s.evidence, "login.ts：空白 token 仍通過驗證"],
    actions: s.actions + 1
  }))
  .addNode("verify", s => ({
    outcome: s.evidence.length > 0 && s.answer.includes("空白 token")
      ? "completed" as const : "rejected" as const
  }))
  .addNode("stop", () => ({ outcome: "budget_exhausted" as const }))
  .addEdge(START, "model")
  .addConditionalEdges("model", s => {
    if (s.decision === "finish") return "verify";
    return s.actions < s.maxActions ? "tool" : "stop";
  }, { tool: "tool", verify: "verify", stop: "stop" })
  .addEdge("tool", "model")
  .addEdge("verify", END)
  .addEdge("stop", END)
  .compile();

const result = await graph.invoke({
  evidence: [], actions: 0, maxActions: 3,
  decision: "tool", answer: "", outcome: "running"
}, { recursionLimit: 20 });
console.log(result.outcome, result.actions); // completed, 1
// 無真模型、檔案 I/O 或 checkpointer。需安裝 SDK 才能執行。
// verify 的文字判斷只用來示範路由，不是正式調查驗收。

第一次 model 看見空的 evidence，要求工具；tool 加入一份證據並增加 actions，固定的邊讓它回到 model。第二次 model 看見證據，提出結論，條件邊帶它進入 verify。此時 outcome 才被更新成 completed。

要接真的工具，就替換 tool 節點的假結果，並在呼叫前驗證參數與權限，同時保留第三章的重試、opId 與 unknown 政策。改成圖，這些責任並不會消失。本章只走成功的讀取路徑。

節點回傳一個欄位，其他資料會不會不見？

model 節點只回傳 decision 和 answer，沒有重建整份 state。LangGraph 會依各欄位的更新規則合併這份「局部更新」，沒更新的欄位照舊保留。簡單欄位預設是「取新值」，所以 evidence 也不會自動追加。

CONCEPT / CHECKPOINT

保存資料，也保存接續執行需要的資訊

Checkpoint 是圖在特定邊界的快照。LangGraph 的 StateSnapshot 可查看 values 與待執行的 next，還包含配置與任務等資訊。Checkpointer 負責保存和讀取這些紀錄。

它保存的是「可重建的執行資訊」，不是把整個 JavaScript stack 冷凍起來。節點內還沒保存的局部變數，恢復後不一定還在。

同時有兩個登入調查，怎麼找回正確的那份？

每次保存都要有共同的識別，才能把同一次調查的快照串起來。LangGraph 用 thread_id 找到這條執行脈絡；同一 thread 可以累積多次 run 的 state。恢復時沿用原 thread，才有機會讀到原本的資料。

thread 不等同一次模型呼叫，也不是作業系統執行緒。你可以為登入 issue 的調查指定一個穩定 ID；另一個獨立調查使用另一個 ID。正式入口還要驗證使用者是否能存取該 thread，不能只憑知道 ID 就取得內容。

thread: login-investigation-05
  input → values: 空證據        next: read
  read  → values: 登入程式證據  next: analyze
                               ↑ 程序停止
  resume 同 thread → 讀取已保存 state → analyze

怎麼先確認「不重做 read」，再談程序重啟？

先在同一個程序裡，讓 analyze 失敗一次：read 已經完成，下一個節點才丟出錯誤。我們先查看快照，再以 null 作為輸入、沿用同一份配置，接續沒做完的執行。這樣可以先看清資料與位置怎麼恢復，不必馬上引入資料庫。

TypeScript · LangGraph SDK／同程序恢復實驗
import { StateSchema, StateGraph, START, END, MemorySaver }
  from "@langchain/langgraph";
import { z } from "zod/v4";
const State = new StateSchema({ evidence: z.string(), answer: z.string() });
let failOnce = true;
let reads = 0;
const graph = new StateGraph(State)
  .addNode("read", () => {
    reads++;
    return { evidence: "login.ts：空白 token 仍通過驗證" };
  })
  .addNode("analyze", s => {
    if (failOnce) { failOnce = false; throw new Error("模擬分析失敗"); }
    return { answer: `根據 ${s.evidence}，需要檢查空白值處理。` };
  })
  .addEdge(START, "read").addEdge("read", "analyze")
  .addEdge("analyze", END)
  .compile({ checkpointer: new MemorySaver() });
const config = {
  configurable: { thread_id: "login-investigation-05" },
  durability: "sync" as const
};
try { await graph.invoke({ evidence: "", answer: "" }, config); }
catch (error) {
  if (!(error instanceof Error) || error.message !== "模擬分析失敗") throw error;
}
const saved = await graph.getState(config);
console.log(saved.values.evidence, saved.next); // 已有證據，下一步 analyze
const result = await graph.invoke(null, config);
console.log(result.answer, reads); // 成功，read 只呼叫一次
// 這是同程序錯誤恢復，不是 kill/restart 實驗。
// MemorySaver 重啟後消失；也沒有真正的檔案或模型呼叫。

預期結果：第一次讀檔成功、分析失敗；getState 看得到證據，且 next 是 analyze。恢復後 analyze 會重新執行，但 read 不會再呼叫。注意這裡是「錯誤後的恢復」；下一章的人工中斷會用不同的恢復輸入。

從概念到工具

MemorySaver、SQLite、PostgreSQL，該用哪一個？

MemorySaver 適合先學保存與讀取，但只存在 RAM。要做本機跨程序實驗，可使用 SqliteSaver 的檔案儲存；需要資料庫後端時，可評估 PostgresSaver。後兩者需另外安裝套件，依官方方式初始化與關閉連線。

換成資料庫，仍要確保資料可持久化、重啟後連到同一儲存、圖版本相容。若使用 LangChain createAgent，也可配置 checkpointer；資料保存政策與存取權限仍需安排。

節點回傳了，資料就一定已經存好了嗎？

還要看寫入的時機。LangGraph 在每個 super-step（引擎執行的一步）的邊界形成 checkpoint。本章用 sync，也就是等保存完成才進下一步；async 讓保存與下一步重疊，所以突然崩潰時，可能還有沒寫完的資料；exit 則是整次執行結束時才保存，中途崩潰就無法逐步恢復。

這些模式只控制引擎「何時」提交資料，底層後端還得真的把資料保住。sync 搭配 MemorySaver，只代表寫進了記憶體，並不會變成磁碟保存。

如果留言已建立，但 checkpoint 還沒存呢？

第三章的問題仍在。建立留言的節點已呼叫外部 API，卻在回傳更新前停止；最新快照可能仍表示「待建立留言」。恢復時節點可能再執行一次。所以操作的 opId 與固定參數要在呼叫前保存，外部服務也要支援冪等或可查核結果。

checkpoint 管的是圖的狀態，receipt 管的是外部效果的證據。兩者不在同一個交易裡，中間就有需要對帳的縫隙。所以快照裡沒有 receipt，不能推論留言還沒建立。

恢復、重試、重播，是同一件事嗎？

本章的恢復接續未完成的圖；工具重試是再次嘗試某個操作；指定舊 checkpoint 做 time travel replay，則可能重新執行其後的節點，包括模型與 API。不能把任何叫 replay 的操作都理解成只讀歷史。

本章是串行圖。並行 super-step 另有 pending writes：已成功節點的保存結果可能用於恢復，避免重跑它們。不要把所有故障描述成整步從頭重做。

欄位只能表達「還沒批准」，沒辦法讓引擎停下來，也沒辦法告訴呼叫者要問使用者什麼。如果在 while 裡一直檢查它，程序就一直在跑；如果直接走到 END，又會把「等待」和「任務結束」混在一起。我們需要的是：能記住停在哪、把問題交出去、之後再接回來的機制。

CONCEPT / HUMAN-IN-THE-LOOP

哪些決定應交給人，流程就停在哪裡

Human-in-the-loop（HITL，人在迴路）是把人的輸入放進執行流程。輸入可能是批准、拒絕、修正內容或補充資料。這裡先限定成「要不要套用眼前這份 patch」，避免一個模糊的「同意」涵蓋之後的所有操作。

誰把批准需求交出去，又怎麼收回答案？

LangGraph 的 interrupt(payload) 在節點內提出需求；payload 用可 JSON 序列化的資料描述待決定內容。引擎透過 checkpointer 保存執行資訊，本次呼叫把需求交回外層，常可從 __interrupt__ 讀到。外層負責顯示提案與接收回覆。

回覆準備好後，用同一個 thread 與 Command({ resume: ... }) 再次呼叫圖。resume 值成為 interrupt 的回傳值，節點才有資料決定走 apply 或 reject。這與第五章用 null 接續故障不同：現在是把外部答案交給一個待回覆的中斷。

patch → approval [interrupt] → 回傳批准需求
              ↓ checkpoint             ↓ 使用者看提案
       同 thread + Command(resume) ← 批准／拒絕
              ↓
       approval 取得答案 → apply 或 reject → END

恢復後，是從 interrupt 的下一行開始嗎？

照程式碼看，好像是從 interrupt 那一行回傳繼續。但實際上，引擎恢復時會讓包含 interrupt 的節點「從開頭重新進入」，跑到 interrupt 才拿到這次的 resume 值。所以 interrupt 前面的程式也會再執行一次。

假設你在 interrupt 之前就套用 patch，再問使用者要不要批准：第一次其實已經改了檔案，恢復時還可能再改一次。正確的順序是：先固定好可審閱的提案，再批准，最後才由獨立的工具節點執行。先用假工具看一次這個順序：

TypeScript · LangGraph SDK／假批准與假工具
import { StateSchema, StateGraph, START, END, MemorySaver,
  interrupt, Command } from "@langchain/langgraph";
import { z } from "zod/v4";
const State = new StateSchema({
  patch: z.string(), approved: z.boolean(),
  outcome: z.enum(["pending", "applied", "rejected"])
});
let approvalEntries = 0; // 只用來觀察重入，不是業務資料
let writes = 0;
const graph = new StateGraph(State)
  .addNode("approval", s => {
    approvalEntries++;
    const reply = interrupt({ question: "套用這份修補嗎？", patch: s.patch });
    // 示範單一 boolean；正式入口還需驗證人員與批准內容。
    if (typeof reply !== "boolean") throw new Error("invalid decision");
    return { approved: reply };
  })
  .addNode("apply", () => {
    writes++; // 假工具，不修改檔案；正式工具需 opId／receipt
    return { outcome: "applied" as const };
  })
  .addNode("reject", () => ({ outcome: "rejected" as const }))
  .addEdge(START, "approval")
  .addConditionalEdges("approval", s => s.approved ? "apply" : "reject",
    { apply: "apply", reject: "reject" })
  .addEdge("apply", END).addEdge("reject", END)
  .compile({ checkpointer: new MemorySaver() });
const config = {
  configurable: { thread_id: "repair-06" }, durability: "sync" as const
};
const paused = await graph.invoke({
  patch: "在 login.ts 加入空白 token 檢查", approved: false, outcome: "pending"
}, config);
console.log(paused.__interrupt__, writes); // 批准需求，0
const result = await graph.invoke(new Command({ resume: true }), config);
console.log(result.outcome, approvalEntries, writes); // applied, 2, 1
// resume:false 改走 reject，writes 為 0。
// MemorySaver 只示範同程序；本例沒有真正驗收修補或安全去重。

第一次執行時 approvalEntries 是 1、writes 是 0；恢復後 approval 節點重新進入，計數變成 2。只有 approved 為 true 才會進 apply，假的寫入次數才增加。這個計數只是讓「重入」看得見，並不表示把業務副作用放在批准之前是安全的。

用 LangGraph interrupt，還是 LangChain middleware？

需要在自訂圖的特定位置詢問資料，就用 LangGraph interrupt／Command。若主要需求是審閱 LangChain Agent 提出的工具呼叫，可用 humanInTheLoopMiddleware，設定哪些工具需要審查與允許的決定，例如批准、編輯或拒絕。

使用者批准的是哪一份 patch？

如果畫面上給使用者看的是 patch A，模型之後改成 patch B，就不能沿用原本的批准。正式系統應保存穩定的 requestId、待執行內容與 payload hash，讓回覆綁定同一份提案；內容一變，就要重新取得決定。Hash 只幫你比對內容，身分與權限仍要另外驗證。

上面的 boolean 範例只展示控制流程。應用入口還要檢查誰回覆、是否仍在等待、批准是否過期，以及回覆是否對應目前提案。重複點擊也要有一致處理；批准後工具若重做，仍沿用第三章的 opId 與 receipt 契約。

等到明天，需要一直保留這次呼叫嗎？

本次 invoke 可先回傳中斷資訊，應用顯示等待狀態；稍後再發起恢復呼叫，不必讓一個工具持續輪詢批准。要跨程序等待，就用第五章的持久化 checkpointer 與相同 thread。MemorySaver 仍會在程序重啟後遺失。

interrupt 本身不替你安排業務批准期限。期限到了如何取消、何時通知、誰允許恢復，以及同 thread 如何避免並行提交，都由應用層安排。後續往 Task Loop 移動時，我們會研究這些跨執行的生命週期。

interrupt 可以包在普通 try/catch 裡嗎？

不要用一般錯誤處理把 interrupt 的控制流程吞掉。中斷與工具故障不同；如果確實要捕捉例外，必須讓中斷訊號繼續交給引擎處理。也不要在恢復相容性未確認時任意增刪或重排同一節點內的 interrupt 呼叫。

本章只處理一個待回覆中斷。多個平行中斷需按 interrupt ID 配對回覆，不能假設一個 boolean 適用所有請求。

Agent 的完成，與使用者的完成，是同一件事嗎？

Agent Runtime 可以檢查自己這次輸出的格式、證據與工具結果；任務協調層則根據整個任務的驗收條件接受產物。例如本次產物是 patch 與測試報告，任務要求還包括正確的 repository 版本與回歸測試。協調層可以呼叫驗收服務，讀取結果後再改任務狀態。

兩層不是重複跑同一個驗收器。內層負責它收到的執行合約，外層負責使用者目標的最終合約。若把模型的「完成」直接映射成任務成功，原本訂好的驗收條件就沒有真正被執行。

CONCEPT / TASK · RUN · ATTEMPT

同一件工作，為什麼需要三種識別？

  • Task：保存使用者的目標與驗收條件。
  • Agent Run：一次有明確輸入、配置與輸出合約的代理執行。
  • Attempt：同一個 Run 的一次嘗試。

這是本教材自己的應用模型，不是各框架共同的標準。

Task login-42：修好登入，通過回歸測試
  ├─ Agent Run investigation-1：調查並提出修補
  │    ├─ Attempt 1：Worker 失聯，結果待查核
  │    └─ Attempt 2：依保存位置恢復原 Run
  └─ Agent Run repair-2：根據驗收缺口補上測試
       └─ Attempt 1：交付新產物 → 任務驗收

第二次 attempt 要維持原 Run 的意圖與輸入，沿用它的恢復關聯。如果改了目標、換了執行合約或重新規劃，就建立新的 Run，並記下它和舊 Run 的關係。等待批准之後的 invoke 也不必自動變成新 Run：第六章是在同一個邏輯執行裡接續的。Run 的邊界由應用定義，要先寫清楚。

Worker 沒有回來，該重試原 Run，還是另派一個？

先查原 Run 的結果與外部效果。若只是傳輸失敗且可以安全恢復，安排同 Run 的新 attempt；若產物已保存，就取回產物，不再盲目執行。若工具效果未知，沿用第三章的 opId 與 receipt 查核。換一個 Worker 不會讓已發生的效果消失。

如果原 Run 已明確結束、驗收指出還需要新的工作，而且總預算允許，就可以建立下一個 Run，把「還缺空白 token 的測試」連同產物引用交給它。這是新的執行合約，但使用者的 Task 仍然是同一個。

Task Loop 是不斷呼叫 Agent 的 while 嗎？

可以有循環，但核心是「決策」：派送一次執行、接收結果，再依任務狀態與政策選擇下一步。等人的時候可以先結束目前的呼叫，等新事件來了再接續；排隊時也不需要一直佔住一個 Agent。這些決策要留下可恢復的紀錄，不能只藏在某個函式執行到哪一行。

queued → 派送 Run → running
                       ├─ 需要批准 → waiting → 回覆 → 接續
                       ├─ 產物就緒 → verifying ─通過→ completed
                       │                       └─缺口→ queued／failed
                       └─ 執行失敗 → 查核 → 原 Run 重試／新 Run／failed
每次決策都檢查：目前執行權、總期限、預算、驗收條件

先不接服務，能把這些決定寫清楚嗎？

可以，先重用第二章的純狀態轉移寫法。下面只保存任務階段、目前的 Run 和計數：最多兩個 Run，每個 Run 最多兩次 attempt。程式不模擬派送是否可靠，只讓我們先看「這個結果能不能改變這個 Task」。正式的模型還要保存產物、批准需求、錯誤分類與總費用。

TypeScript · 純狀態規則／非框架 API
type TaskStatus = "queued" | "running" | "waiting" | "verifying"
  | "completed" | "failed";
type Task = {
  taskId: string; status: TaskStatus;
  runId: string | null; attempt: number; runsStarted: number;
  maxRuns: number; maxAttempts: number;
};
type Event =
  | { kind: "start_run"; runId: string }
  | { kind: "retry_attempt"; runId: string }
  | { kind: "needs_input" | "resume" | "candidate"; runId: string }
  | { kind: "verified"; runId: string; passed: boolean }
  | { kind: "run_failed"; runId: string };

function reduceTask(t: Task, e: Event): Task {
  if (t.status === "completed" || t.status === "failed")
    throw new Error("task already closed");
  if (e.kind === "start_run") {
    if (t.status !== "queued" || t.runsStarted >= t.maxRuns)
      throw new Error("cannot start run");
    return { ...t, status: "running", runId: e.runId,
      attempt: 1, runsStarted: t.runsStarted + 1 };
  }
  if (e.runId !== t.runId) throw new Error("stale run result");
  if (e.kind === "retry_attempt" && t.status === "running") {
    if (t.attempt >= t.maxAttempts) throw new Error("attempt limit");
    return { ...t, attempt: t.attempt + 1 };
  }
  if (e.kind === "needs_input" && t.status === "running")
    return { ...t, status: "waiting" };
  if (e.kind === "resume" && t.status === "waiting")
    return { ...t, status: "running" };
  if (e.kind === "candidate" && t.status === "running")
    return { ...t, status: "verifying" };
  if ((e.kind === "run_failed" && t.status === "running") ||
      (e.kind === "verified" && t.status === "verifying")) {
    if (e.kind === "verified" && e.passed)
      return { ...t, status: "completed" };
    return { ...t, status: t.runsStarted < t.maxRuns ? "queued" : "failed" };
  }
  throw new Error("invalid transition");
}
// 純狀態規則：不派送、不呼叫模型、不保存，也不排程重試。
// 呼叫者要先確認錯誤可重試、外部效果可查核，再送入事件。
// runId 比對只拒絕舊結果；正式系統還要 attempt 識別、交易與 fencing。

例如 run-1 的 attempt 失敗，若允許安全恢復，就增加 attempt，taskId 與 runId 不變；若 Run 結束但任務還可繼續，Task 回到 queued，下一個 start_run 建立 run-2。只有 verified 且 passed 為 true，Task 才到 completed。

超過重試上限時，這段程式只把錯誤交回呼叫者，不會自動排程或關閉 Task；呼叫者還要決定怎麼結束原本的 Run。故障分類、延遲與總期限也不在這個函式裡。先把「規則」和「執行」分開，下一章才好討論工作怎麼送到 Worker。

跨執行的等待與協調，有哪個工具能承接？

為什麼不直接呼叫一個 Agent，就等它做完？

小型實驗可以直接呼叫。但修復任務一多，或 Worker 需要重啟，「發出任務」和「執行任務」的步調就對不上了。所以中間放一個 Queue：協調層把工作丟進去，Worker 有空時再來拿，做完交回結果。協調層不必知道每個 Worker 現在在哪。

CONCEPT / QUEUE · WORKER

排隊的是工作，執行的是程序

Queue 負責暫存並派送工作；Worker 是真正取工作、執行的程序；Agent Runtime 是 Worker 執行的代理邏輯。同一個 Worker 可以處理多個工作，但要限制同時做幾個，並讓每個工作的檔案與上下文互相隔離。

Task Orchestrator → 工作 job-2 → Queue

Task Orchestrator ← 接受結果與任務驗收

這裡的 job 指「應用層的工作項目」，內容有 taskId、runId、輸入與執行配置；大型產物只放 URI 與 hash。要小心：Temporal 也有 Workflow Task、Activity Task，那是引擎自己的工作單位，跟使用者的 Task 是兩回事。看到相似的名字，先問它在哪一層。

Worker 一取走工作，就能從 Queue 刪掉嗎？

假設 Worker A 一取走 run-2 就把它從 Queue 刪掉，結果 A 在寫完測試前當機了。現在 Queue 裡沒有 run-2，也沒有人知道它做到一半。

所以 Queue 的做法是：先把工作「借」給 A，等 A 把結果存好、回報完成，才真的刪掉。這個「回報完成」叫確認（Acknowledgement，簡稱 Ack）。各家產品的名稱不一樣，例如 SQS 是用「刪除訊息」表示確認。

還有一個縫隙：結果存好了，但確認訊息遺失，工作就會再被派一次。所以 Worker 重新拿到工作時，要先查有沒有已保存的 job／Run 回執（receipt）；已經有可接受的結果，就直接交回去。Queue 讓工作有機會再做一次；第三章的冪等與查核，確保再做一次不會多出錯誤的效果。

沒有完成回報，代表 Worker 已經死了嗎？

沒收到完成回報，不代表 Worker 死了：可能只是網路慢，也可能程序還活著卻卡住。但協調層不能一直等，所以給這次執行一段有限的時間：期限內歸這個 Worker 做，逾期就可以把工作派給別人。

CONCEPT / LEASE · HEARTBEAT

執行權有期限，存活訊號用來延續它

租約（Lease）就是「這份工作在 12:00 之前歸你做」。時間到了還沒交，Queue 就當你不做了，可以派給別人。

工作如果要做很久，Worker 可以定期發心跳（Heartbeat）說「我還在做」，租約就會延長。

兩個容易誤會的地方：

  • 心跳只代表程序還活著，不代表工作做完，也不代表模型沒卡住。
  • 租約不保證只有一個 Worker 在做：A 太慢被判逾期、B 接手後，A 其實可能還在跑。這就是為什麼後面要擋掉 A 的結果。

期限太短，正常的工作也會被誤判逾期、重複派送；太長，Worker 失聯後要等很久才能換手。建議先量測工作實際花多久，再訂續租與總期限。另外，總期限屬於第七章的 Task 政策：不能因為一直發心跳，就讓任務無限延長。

進階閱讀：競爭與提交邊界

租約過期，舊 Worker 就停止了嗎？

不一定。想像 Worker A 暫時連不上協調層，租約過期；Worker B 取得新租約並開始處理。A 恢復連線後仍可能提交結果。若只檢查 runId，兩者同屬 run-2，舊結果就可能覆蓋新結果。

我們為每次取得執行權加一個世代編號（generation），提交時一併帶上；保存端只接受目前有效的世代。這種把失效的 Worker 擋在寫入邊界的做法叫 Fencing。正式方案必須讓受保護的儲存或服務檢查執行權，不能只在 Worker 自己判斷。單調遞增 token 與下游拒絕較舊 token 的原理參考 Kleppmann 原文；本例直接核對目前 job 租約，不是外部服務的完整 fencing protocol。

  status: "queued" | "leased" | "done";
  generation: number; owner: string | null; expiresAt: number;
};
type Claim = { jobId: string; owner: string; generation: number };
const job: Job = {
  jobId: "job-1", taskId: "login-42", runId: "run-1",
  status: "queued", generation: 0, owner: null, expiresAt: 0
};
// 同步記憶體示範：正式 claim 必須由儲存端原子提交。
function claim(owner: string, now: number): Claim | null {
  if (job.status === "done") return null;
  if (job.status === "leased" && now < job.expiresAt) return null;
  job.status = "leased"; job.owner = owner;
  job.generation += 1; job.expiresAt = now + 10;
  return { jobId: job.jobId, owner, generation: job.generation };
}
function complete(c: Claim, now: number): boolean {
  if (job.status !== "leased" || c.jobId !== job.jobId ||
      c.owner !== job.owner || c.generation !== job.generation ||
      now >= job.expiresAt) return false;
  job.status = "done";
  return true;
}

console.log(complete(b, 12)); // true
// 時間單位是模擬秒。沒有網路、心跳、artifact 或外部工具。
// complete 只保護此 job；外部寫入仍要自己的執行權／冪等契約。

「請執行工作」與「工作已領取」，是同一種紀錄嗎？

前者是 Command（命令），表達想做的事，仍可能被拒絕；後者是 Event（事件），表達已接受的事實。領取命令先經過第八章的租約與原子檢查，成功後才留下 Claimed。不要把收到請求直接記成成功。

失敗或拒絕也可以留下事實，例如 ResultRejected。它說明一次提交被拒絕，沒有宣稱該提交成為任務結果。事件名稱與內容要讓讀者看得出差別。

CONCEPT / EVENT HISTORY · PROJECTION

留下事實，再從事實讀出目前狀態

Event History 是依序追加的事件紀錄；Projection（投影） 是把事件轉成目前狀態或查詢畫面的規則。若以事件作為權威資料、由它重建狀態，便採用了 Event Sourcing 的思路。

注意：有 audit log，不等於採用了 Event Sourcing。如果「權威資料」仍是狀態表，事件只是附帶的紀錄，就要說清楚兩者的關係。本章刻意選擇以事件作為重建的來源。

重建畫面時，會再叫 Worker 修一次程式嗎？

不會。我們重用第二章的純函式：每讀到一個事實，計算下一份資料。ResultSaved 讓投影記住產物引用，不再產生 patch；Verified 讀取已保存的驗收事實，不再次執行測試。資料投影重播與外部操作重試，必須分開。

TypeScript · 純資料投影／非工作流程引擎
type HistoryEvent =
  | { seq: number; id: string; kind: "created" }
  | { seq: number; id: string; kind: "claimed"; generation: number; owner: string }
  | { seq: number; id: string; kind: "lease_expired"; generation: number }
  | { seq: number; id: string; kind: "result_rejected"; generation: number }
  | { seq: number; id: string; kind: "result_saved"; generation: number; artifact: string }
  | { seq: number; id: string; kind: "verified"; passed: boolean };
type View = {
  status: "absent" | "queued" | "running" | "verifying" | "completed" | "failed";
  generation: number; owner: string | null; artifact: string | null;
};
const empty: View = { status: "absent", generation: 0, owner: null, artifact: null };
function project(v: View, e: HistoryEvent): View {
  switch (e.kind) {
    case "created": return { ...v, status: "queued" };
    case "claimed": return { ...v, status: "running",
      generation: e.generation, owner: e.owner };
    case "lease_expired": return { ...v, status: "queued", owner: null };
    case "result_rejected": return v; // 保留稽核線索，不改任務結果
    case "result_saved": return { ...v, status: "verifying", artifact: e.artifact };
    case "verified": return { ...v, status: e.passed ? "completed" : "failed" };
  }
}
function rebuild(events: HistoryEvent[]): View {
  let v = empty;
  events.forEach((e, index) => {
    if (e.seq !== index + 1) throw new Error("history gap or wrong order");
    v = project(v, e);
  });
  return v;
}
// 前提：這是儲存端已接受、依序提交的事實，不是未驗證請求。
// project 不執行工具，也不判斷新請求是否合法；那是命令處理端責任。
// 此模型尚無 append 儲存、去重、交易、outbox 或版本遷移。

rebuild 從空狀態開始，依序套用事件；序號有缺口就拒絕，免得用不完整的歷史冒充正確結果。這裡假設事件已經由命令端合法接受，所以 project 不再做租約授權。「驗證新請求」和「重建既有事實」是兩個不同的入口。

同一回報來兩次，歷史也追加兩次嗎？

先區分事件 ID、命令 ID 與序號：eventId 識別已提交事實，commandId 協助辨識同一請求的重送，seq 定義任務內的提交順序。正式追加可帶 expectedVersion，由儲存端原子檢查版本與去重，再追加事件；兩個提交者不能都成功使用同一舊版本。這是本教材的應用契約，不是只加一個欄位就得到的保證。

投影消費者也可能重收事件，可在同一交易保存投影與已處理序號。遇到缺口先補齊，遇到已處理的同一事件則跳過；同序號卻內容不同應視為一致性錯誤。不要用 Worker 本機時間來排序跨機器事實。

事件存好了，Queue 卻沒收到工作，怎麼辦？

如果先追加「準備派送」，再送 Queue，程序可能在兩者之間停止。反過來先送 Queue，也可能讓工作已執行卻沒有可靠的派送紀錄。兩次提交之間的縫隙，並沒有因為多了 History 就消失。

CONCEPT / TRANSACTIONAL OUTBOX

把待送訊息與業務紀錄一起提交

Transactional Outbox 把業務變更與待發送訊息放進同一資料庫交易，之後由 relay 送到 Queue。relay 仍可能重送，所以消費端仍需去重與冪等。它解決本地交易與發送之間的漏送縫隙，沒有替外部工具建立 exactly-once 效果。

    CONCEPT / WORKFLOW · ACTIVITY

    誰決定下一步，誰真正做外部工作？

    Workflow 表達協調流程：先提出修補、再套用、最後驗收（10B 會在套用前加上「等批准」）。Activity 執行外部操作：呼叫 Agent Runtime、讀寫檔案、存取服務或執行測試。模型的輸出有不確定性，所以模型呼叫也放在 Activity 的邊界內。

    Worker 是執行 Workflow 與 Activity 程式的程序，Temporal Service 負責保存執行歷史並協調工作。兩者角色不同：關閉 Worker，不會刪掉 Service 裡的流程紀錄。

    Worker 重啟，Workflow 會從哪一行開始？

    不要以為原本的 JavaScript stack 還留著。需要重建時，SDK 會用 History 把 Workflow 程式「重播」一遍，讓它走回已知的位置。已經記錄完成的 Activity，重播時直接取歷史結果；Workflow 不會因為重播就再執行一次那個 Activity 的外部程式。

    這跟第九章的純投影重建不一樣：引擎還要讓程式產生與歷史相容的命令。它也跟 Activity retry 不同：Activity 還沒被記錄完成時，仍可能再執行一次。例如外部 patch 已經套用、完成回報卻遺失，這就是第三章的「結果未知」問題。

    CONCEPT / DETERMINISM · REPLAY

    同一份歷史，能走出相容的決策嗎？

    確定性（Determinism）是指：Workflow 重播時，要產生與歷史相容的命令序列。所以不要在 Workflow 裡直接讀檔、fetch 或呼叫模型來決定路由；先透過 Activity 取得並保存結果，再依它決策。

    TypeScript SDK 的 Workflow 執行環境提供確定性的時間與隨機行為，但這不代表任意套件都能放進 Workflow。改動已經執行過的路徑上的命令順序，也可能造成不相容，所以需要版本策略與歷史重播測試。

    TypeScript · Temporal Workflow SDK
    // workflows.ts：Workflow 不直接呼叫模型、檔案或 HTTP。
import { proxyActivities, defineSignal, setHandler, condition }
  from "@temporalio/workflow";
import type * as activities from "./activities";
export const approvePatch = defineSignal<[
  { requestId: string; payloadHash: string; approved: boolean }
]>("approvePatch");
const { proposePatch, applyPatch, verifyPatch } =
  proxyActivities<typeof activities>({
    startToCloseTimeout: "2 minutes",
    scheduleToCloseTimeout: "6 minutes",
    retry: { maximumAttempts: 3 }
  });
export async function repairWorkflow(taskId: string) {
  let proposal: Awaited<ReturnType<typeof activities.proposePatch>> | undefined;
  let decision: boolean | undefined;
  // 先註冊 handler；本例只接受提案已產生後的合法回覆。
  setHandler(approvePatch, reply => {
    if (!proposal || decision !== undefined) return;
    if (reply.requestId !== proposal.requestId ||
        reply.payloadHash !== proposal.payloadHash) return;
    decision = reply.approved;
  });
  proposal = await proposePatch(taskId);
  const received = await condition(() => decision !== undefined, "24 hours");
  if (!received) return { status: "approval_expired" as const };
  if (!decision) return { status: "rejected" as const };
  const artifact = await applyPatch({
    taskId, proposal, opId: `${taskId}:apply:${proposal.requestId}`
  });
  const passed = await verifyPatch(artifact);
  return { status: passed ? "completed" : "verification_failed", artifact };
}
// 入口服務驗證 caller 權限；handler 比對目前提案、只收第一個決定。
// Activity retry 沿用同一參數與 opId；applyPatch 服務仍需冪等／查核。
// 24 小時只限制批准等待；不是整個 Task 的總期限。

    先啟動本地 Temporal Service，再讓 Worker 註冊 repairWorkflow 與這三個 Activity；Client 使用唯一 workflowId 啟動。使用者回覆由入口服務檢查權限，再送 approvePatch Signal。activities.ts 沿用 10A 的版本（可把 15 秒等待拿掉）。本章沒有在 HTML 裡執行 SDK。

    Signal 已送出，就代表 patch 已套用了嗎？

    Signal 只是把訊息交給 Workflow，不會直接回傳業務結果。送出成功，不等於 handler 接受了提案，更不等於 applyPatch 完成了。本例對錯誤的 hash、重複的決定，以及提案產生之前就送來的回覆，一律忽略；產品入口應該只對「已經顯示給使用者的待批准提案」送回覆，並提供狀態查詢。

    如果需要拿到「接受或拒絕」的業務回傳，可以評估 Update；只想讀取目前狀態，用 Query，它不會改變 Workflow 狀態。Signal、Update、Query 解決不同的互動需求，不能拿查詢當批准命令。

    等一天，需要一直佔著一個 Activity 嗎？

    不用。本例的批准等待放在 Workflow 裡，沒有用 Activity 無限輪詢。等待與期限由引擎管理，Worker 可以去處理其他工作。就算所有 Worker 都離線，Service 仍會保存訊息與計時狀態；只是要等 Worker 回來，Workflow 程式才會繼續往下處理。

    兩分鐘、六分鐘與二十四小時，分別限制哪裡？

    設定本例用途仍需注意
    startToCloseTimeout：2 分鐘單次 Activity attempt 的執行上限逾時不證明遠端效果未發生，也不保證舊程式立即停止
    scheduleToCloseTimeout：6 分鐘該 Activity 從排程到完成，包含排隊與重試的總上限不等於整個 Task 的期限
    maximumAttempts：3Activity 最多三次嘗試，包含首次時間上限可能先到；業務拒絕不應盲目重試
    condition：24 小時提案產生後的批准等待期限批准、套用與驗收後續還要自己的預算

    這些數字只是實驗用的政策。長時間的 Activity 可以用 heartbeat 回報進度、協助偵測失聯，但仍需要工具的取消機制與效果查核；Workflow 的 retry 和 Activity 的 retry 也不是同一層。整個 Task 的期限、費用、允許幾個 Agent Run，仍由第七章的任務政策決定。

    從概念到工具

    Temporal 與 LangGraph，要各自記住什麼？

    進階：片段 receipt、checkpoint 與雙層恢復契約

    一個狀態，一個權威

    Task Orchestrator 擁有 Task/Execution status、批准 request 與總預算；Agent Runtime checkpoint 擁有 messages、工具路由與圖狀態；工具 ledger 擁有 opId 的外部結果。Temporal History 記錄片段結果，不放整份聊天與 artifact。Checkpoint ID、thread ID 與 artifact URI 建立跨層關聯。

    兩次提交之間的縫隙

    Graph checkpoint 成功後、Activity completion 送達前 Worker 死亡，Temporal 可能重試同一片段。使用穩定 segmentId、持久化片段 receipt 與同 thread 排他執行；重試先查 receipt。若 receipt 未寫入，依 checkpoint 判斷恢復或從已完成 state 重建結果。不能把 completed graph 當新 input 再啟動。

    寫 checkpoint 與 receipt 若不是同交易，adapter 必須能判讀兩者不一致並對帳。receipt 與 Temporal Service 的完成記錄也沒有跨系統原子提交；重送既有 receipt 是協定的一部分。Tool ledger 則封閉外部效果的縫隙。

    等待與重試分工

    Agent Runtime interrupt 回傳 needs_input；Activity 結束，Workflow 等 Signal，再呼叫新 segment 恢復圖。Activity retry 處理傳輸與程序錯誤；圖重試處理特定節點暫時錯誤；Task Orchestrator 管整體預算與交接。各層不要各自無限重試，否則總嘗試次數會相乘。

type SegmentInput = {
  executionId: string; threadId: string; segmentId: string;
  graphVersion: string; resume?: { requestId: string; approved: boolean };
};
type SegmentResult =
  | { kind: "completed"; artifactUri: string }
  | { kind: "needs_input"; requestId: string; payloadHash: string }
  | { kind: "budget_exhausted"; checkpointId: string };
async function runSegment(input: SegmentInput): Promise<SegmentResult> {
  return withExclusiveThread(input.threadId, async () => {
    const previous = await receipts.find(input.segmentId);
    if (previous) return previous;
    // adapter 辨識：未開始 / 中斷 / 失敗 / 已完成 checkpoint。
    const result = await adapter.resumeOrStart(input);
    await receipts.saveUnique(input.segmentId, result);
    return result;
  });
}

import { condition, defineSignal, setHandler, proxyActivities }
  from "@temporalio/workflow";
import type { SegmentInput, SegmentResult } from "./contracts";
const decisionSignal = defineSignal<[
  { requestId: string; payloadHash: string; approved: boolean }
]>("decision");
const { runSegment } = proxyActivities<{
  runSegment(input: SegmentInput): Promise<SegmentResult>
}>({
  startToCloseTimeout: "5 minutes",
  scheduleToCloseTimeout: "15 minutes",
  retry: { maximumAttempts: 3 }
});
export async function taskWorkflow(executionId: string) {
  const decisions: Record<string, { payloadHash: string; approved: boolean }> = {};
  setHandler(decisionSignal, d => {
    // 入口服務已驗證 caller、requestId 與 payloadHash；第一個決定生效，避免批准被重送覆寫。
    if (!decisions[d.requestId]) decisions[d.requestId] = d;
  });
  let resume: SegmentInput["resume"];
  for (let segment = 0; segment < 10; segment++) {
    const result = await runSegment({
      executionId, threadId: executionId,
      segmentId: `${executionId}:segment:${segment}`,
      graphVersion: "agent-v1", resume
    });
    if (result.kind === "completed") return result;
    if (result.kind === "budget_exhausted") return result;
    const received = await condition(() =>
      decisions[result.requestId]?.payloadHash === result.payloadHash,
      "24 hours");
    if (!received) return { kind: "approval_expired" };
    const d = decisions[result.requestId];
    if (!d.approved) return { kind: "rejected" };
    resume = { requestId: result.requestId, approved: true };
  }
  return { kind: "segment_limit" };
}

    候選只是建議，預留成功才取得開始資格

    先把候選選擇寫成純函式，能看出差別嗎？

    下面輸入同一份登入工作的需求，先排除不相容 Worker，再檢查租戶與供應商訊號，最後比較空位比例。它回傳 candidate、wait 或 unroutable，讓應用知道下一步應嘗試預留、等待或處理配置。

    TypeScript · 純候選選擇／非分散式調度器
    type Worker = {
  id: string; capabilities: string[]; graphVersion: string;
  allowedTenants: string[]; capacity: number; active: number;
};
type Job = { tenant: string; capability: string; graphVersion: string };
type Limits = { tenantActive: number; tenantMax: number; providerReady: boolean };
type Choice = { kind: "candidate"; workerId: string }
  | { kind: "wait"; reason: "tenant_limit" | "provider_limit" | "no_slot" }
  | { kind: "unroutable" };
function choose(job: Job, workers: Worker[], limits: Limits): Choice {
  const compatible = workers.filter(w =>
    w.capabilities.includes(job.capability) &&
    w.graphVersion === job.graphVersion &&
    w.allowedTenants.includes(job.tenant));
  if (!compatible.length) return { kind: "unroutable" };
  if (limits.tenantActive >= limits.tenantMax)
    return { kind: "wait", reason: "tenant_limit" };
  if (!limits.providerReady)
    return { kind: "wait", reason: "provider_limit" };
  const available = compatible.filter(w => w.active < w.capacity)
    .sort((a, b) => a.active / a.capacity - b.active / b.capacity
      || a.id.localeCompare(b.id));
  return available.length
    ? { kind: "candidate", workerId: available[0].id }
    : { kind: "wait", reason: "no_slot" };
}
// 純候選選擇：不保留 slot，也不是 Temporal SDK API。
// 正式 admission 需在共享儲存端原子檢查並保留各項額度。
// providerReady 只是簡化訊號，沒有實作 token/minute 計量。

    呼叫 choose 不會增加 active，重複呼叫仍可能選到同一 Worker。正式 admission 要重新確認版本與額度，預留失敗就重新選擇或排隊。執行完成、取消與失聯也需釋放或回收資源；預留紀錄要綁執行識別與世代，避免舊 Worker 回來釋放新租約。

    加十台 Worker，就能多呼叫十倍模型嗎？

    如果瓶頸是供應商的每分鐘請求或 token 配額，增加 Worker 只會讓更多工作一起遇到限流。並行數（Concurrency）限制同時有幾份工作；速率限制（Rate Limit）限制一段時間內能發出多少請求或 token。兩者要分開計量。

    供應商額度要依實際共用的範圍管理，並在模型請求真正送出前再檢查。收到限流回應時，依服務契約做有上限的等待，同時降低送入速度；重試的成本也要算進原本的 Task。範例的 providerReady 只表示「暫時能不能開始」，沒有實作完整的流量控制。

    CONCEPT / BACKPRESSURE

    下游做不完，入口該怎麼回應？

    背壓（Backpressure）是把「容量不夠」的訊息傳回上游：暫停派送、延後接受，或回傳可重試的忙碌結果。Queue 不能無限長；要定義等待上限、過期與取消，讓使用者知道工作是還在排隊，還是已經做不成了。

    進階閱讀：優先級與租戶公平

    大租戶一次送一百份，小租戶只能等嗎？

    若再加優先級，要考慮低優先工作是否一直輪不到。Aging 是隨等待時間增加機會的一種政策，並非只加欄位就保證不會飢餓；必須明確實作、限制高優先流量，並量測最老工作的等待時間。本章的候選函式尚未實作跨任務公平排序。

    應該先測模型答得好不好，還是流程接得回來？

    先固定模型決策：讀登入檔、提出同一份 patch、等待批准、套用、驗收。這讓相同輸入走出可比較的路徑。若模型每次都選不同工具，就很難分辨失敗來自模型變化，還是恢復契約。流程穩定後，再加入真模型品質測試。

    CONCEPT / INVARIANT · FAULT INJECTION

    故障發生後，哪些規則仍必須成立？

    Invariant（不變條件）是每個情境都要維持的規則，例如未批准不能套用、舊世代不能提交、費用不超預算。Fault Injection（故障注入）則刻意在提交邊界製造中斷，檢查規則是否仍成立。

    「最後成功」只是一個結果，還要檢查副作用次數、產物、授權與等待原因。另外要注意：「效果最多一次」的要求，前提是工具服務有實作冪等契約；不支援冪等或查詢的工具，應該測試能不能保留 unknown，而不是宣稱已經去重。

    在哪裡切斷，才會碰到真正的縫隙？

    先走一遍正常路徑，再挑兩份紀錄之間的縫隙切斷。每次只改一個故障位置，並保存注入前後的資料，才能解釋「為什麼恢復是從那裡開始」。

    故障位置應觀察的證據預期邊界
    工具效果成功，回應遺失同 opId 的 ledger／遠端 receipt支援冪等時重送不新增效果；否則查核或 unknown
    Checkpoint 已存，segment receipt 未存原 thread、checkpoint、片段狀態adapter 查核內層結果，不盲目從頭執行
    Receipt 已存，Activity completion 遺失穩定 segmentId 與 receiptActivity 重試取回既有結果
    等待批准時 Worker 停止提案 hash、批准回覆、History相容 Worker 回來後接續，拒絕或過期不套用
    重複批准／並行 resume第一個有效決定、執行世代應用 adapter 只接受合法接續，不新增效果
    模型限流／容量滿載等待原因、嘗試、費用與最老工作年齡有界等待與背壓，不繞過共用配額
    取消時工具仍在執行取消請求、遠端效果與查核結果取消不冒充回滾；保留已發生或未知效果
    新版本接手舊任務代表性 History、舊 checkpoint 與 schemaWorkflow replay 與圖相容性分別驗證

    怎麼讓測試報告真的檢查證據？

    測試工具要去讀真實的測試 ledger 與狀態，不能讓被測程式自己填一個 passed。下面先寫報告驗證器：它檢查冪等工具的效果紀錄、批准約束、預算與明確的結果；注入故障與收集資料，則由你的 harness 負責。

    TypeScript · Node 報告驗證器／需接自訂 harness
    import assert from "node:assert/strict";
type Report = {
  outcome: "completed" | "failed" | "waiting" | "unknown";
  waitReason?: string;
  reconciliationRef?: string;
  artifactHash?: string;
  testsPassed: boolean;
  approved: boolean;
  effects: { opId: string; count: number }[];
  spent: number;
  budget: number;
  noCrossTenantAccess: boolean;
};
function verifyReport(r: Report) {
  assert(r.noCrossTenantAccess);
  assert(Number.isFinite(r.spent) && r.spent >= 0);
  assert(Number.isFinite(r.budget) && r.budget >= 0);
  assert(r.spent <= r.budget);
  // 前提：這些 opId 對應具冪等契約的假工具。
  assert(r.effects.every(e => Number.isInteger(e.count) && e.count >= 0 && e.count <= 1));
  assert(r.approved || r.effects.every(e => e.count === 0));
  if (r.outcome === "completed") {
    assert(r.testsPassed && r.artifactHash);
  }
  if (r.outcome === "waiting") assert(r.waitReason);
  if (r.outcome === "unknown") assert(r.reconciliationRef);
}
// 自訂教學介面：不是 Temporal 或 LangGraph 測試 API。
// effects 只計算需要批准的寫入，不包含讀檔。
// harness 還須核對所有預期 opId，不能以空清單冒充完整證據。
// 真正的隔離、計量、效果與恢復時間需由測試環境收集。

    unknown 不一定代表驗收失敗：如果工具能力不足，安全地保留未知結果，可能正是正確的政策。但報告必須附查核引用和負責的流程。completed 則需要產物與測試證據。兩種結果不能混成同一個「已處理」。

    出了事，要用哪個識別把證據接起來？

    以 taskId 串起使用者目標，再記錄 Agent Run、Temporal workflowId／runId、Activity attempt、segmentId、threadId、checkpointId 與 opId。它們識別不同生命週期，不要共用一個 attempt 名稱。大 patch 與測試 log 放在產物儲存，狀態與歷史保存 URI、hash 及必要摘要。

    量測 Queue 等待、恢復時間、checkpoint 寫入、unknown 年齡與每 Task 成本。先定義觀察起終點，再訂 SLO。例如「測試環境 Worker 恢復後兩分鐘內接續」是本次實驗目標，不是框架保證；批准等待要與執行時間分開計算。紀錄避免憑證與不必要的私密資料，並定義存取與保留政策。

    換版本或還原備份，能只測新任務嗎？

    不能。保存代表性開啟及已結束 Workflow History，用新 Worker 程式做 replay；另外保存舊圖的 checkpoint，驗證 schema、節點與恢復輸入仍相容。Workflow replay 不會替你證明 LangGraph 遷移正確，也不會驗證外部工具效果。

    再做一次備份還原：恢復 checkpoint、receipt 與產物引用，檢查它們是否指向相同操作。記錄可接受的資料損失窗口（RPO）與還原時間（RTO），以及不一致時的對帳方式。先在隔離環境演練，再安排逐步部署與回復路徑。

    術語表

    教材中反覆出現的詞。正文裡虛線底線的詞，滑鼠移上去或按一下就會顯示定義。後面的「首見章」可跳回該章。

    本教材的用詞約定

    • Worker：執行工作的程序；文中不另用「執行者」稱呼它。
    • 縫隙 vs 缺口：縫隙是兩次提交之間可能出錯的空檔；缺口是缺少的資料、保護或下一步（例如序號缺口）。
    • 逾時 vs 逾期：逾時（timeout）是「等太久不等了」；逾期（expired）是租約或批准已過期限。
    • 重試 vs 重送：重試是再做一次操作；重送是把同一個請求或訊息再送一次。
    • 世代：每次換手就加一的編號，程式碼裡寫作 generation。
    • 預留：先把容量佔住，別人不能再用；與「保留」資料或結果不同。
